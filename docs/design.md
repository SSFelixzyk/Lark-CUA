# CUA-Lark 系统设计文档

> 一个以视觉多模态大模型为核心，面向测试工程师的飞书桌面端自动化测试 Agent

---

## 一、项目定位

### 目标用户

测试工程师（QA）。他们的工作流程是：编写测试用例 → 执行测试 → 看报告。CUA-Lark 替代其中"执行测试"这一环。

### 核心价值

传统 GUI 自动化（Selenium / PyAutoGUI 脚本）依赖元素选择器，飞书 UI 一旦迭代，脚本就失效。CUA-Lark 用视觉理解代替选择器，**像真实用户一样看着屏幕操作**，天然对 UI 变更有鲁棒性。

### 产品形态

接受**自然语言测试文档或测试用例**作为输入，自动生成结构化测试 DSL，执行后输出带截图轨迹的测试报告。

```
[测试文档 / 自然语言用例]
         ↓  (模型生成)
[结构化测试 DSL]
         ↓  (Agent 执行)
[操作轨迹 + Pass/Fail 报告]
```

## 三、各层详细设计

### 3.1 DSL 生成层

测试工程师输入自然语言（测试文档片段、用例描述、需求说明），模型将其转换为结构化的测试 DSL。DSL 是执行层的"脚本"，也是报告的结构骨架。

#### DSL 格式

```yaml
test_case_id: im_send_message_001
product: IM
description: 在IM中搜索测试群并发送消息
precondition: 飞书已登录，测试群已存在

steps:
  - id: step_1
    intent: "点击左侧搜索图标，搜索'测试群'"
    checkpoint: "搜索结果列表中出现名称含'测试群'的群聊"

  - id: step_2
    intent: "点击进入测试群聊天界面"
    checkpoint: "聊天窗口标题显示'测试群'"

  - id: step_3
    intent: "在输入框输入'Hello World'并发送"
    checkpoint: "聊天记录底部出现内容为'Hello World'的消息气泡"

expected_result: PASS
timeout_per_step: 30s
max_retries: 2
```

#### 生成方式

```
输入：自然语言（"测试IM发送消息功能"）
  ↓
Doubao：按 DSL schema 生成 YAML
  ↓
人工可选审查 / 直接执行
```

生成 prompt 要求模型严格按 schema 输出，checkpoint 必须是**具体的视觉可观测断言**（可在截图上判断的），不能是抽象描述（如"发送成功"）。

---

### 3.2 Task Decomposer（轻量，可选）

**触发条件**：测试用例涉及多个飞书子产品联动时启用（如：IM 收到日历邀请 → 跳转日历确认 → 返回 IM 验证状态）。

**设计原则**：不做复杂规划，仅将一条大用例按**子产品边界**切分为若干子任务，每个子任务独立跑 ReAct 循环，上一个子任务的最终状态截图作为下一个的起始上下文。

单产品用例直接跳过此层，进入 ReAct 循环。

---

### 3.3 ReAct 执行循环

这是系统核心，所有实际操作都在这里发生。

#### 循环结构

```
初始化：加载系统 prompt + 测试用例 intent 序列
  ↓
[Round N]
  1. 系统截图（mss 库，全屏或飞书窗口区域）
  2. 截图 + 历史对话 → Doubao 2.0
  3. 模型输出 Thought + Action
  4. action_parser 解析 Action → pyautogui 代码
  5. 执行 pyautogui 代码
  6. 等待渲染（固定 sleep + 可配置）
  ↓
到达 checkpoint 时 → 触发结构化断言验证
  ↓
loop until: finished() / failed() / 超时 / max_steps
```

#### 截图策略

**系统固定截图，不由模型控制**。每轮循环开始时系统自动截图，模型只负责看图决策。`wait()` 动作的语义是让系统多等几秒后再截图，而不是模型主动截图。

原因：
- 确定性：截图时机固定，循环状态机可预测
- 可审计：每步截图自动留档，报告有完整 evidence
- 防止模型跳过观察步骤

#### 历史上下文管理

多轮对话消息格式（与 UI-TARS / Doubao 对齐）：

```
[system: 飞书测试 Agent prompt + 当前步骤 intent]
[user: screenshot_t0]
[assistant: Thought+Action_t0]  ← 用 add_box_token() 处理坐标标记
[user: screenshot_t1]
[assistant: Thought+Action_t1]
...
[user: screenshot_current]
```

历史长度控制：保留最近 N 轮（建议 5-8 轮），防止 token 超限。

#### 系统 Prompt

基于 `COMPUTER_USE_DOUBAO` 改造，针对飞书场景增加：
- 飞书常用 UI 导航知识（左侧导航栏图标说明、常见弹窗模式）
- 当前步骤的 intent 和 checkpoint（每轮动态注入）
- 明确的 `failed()` 动作（测试场景必要）

```
你是一个飞书桌面端自动化测试 Agent。
当前测试步骤：{current_intent}
本步骤通过条件：{current_checkpoint}

## 飞书界面说明
- 左侧导航栏从上到下：消息、日历、云文档、多维表格、视频会议、邮箱
- 顶部搜索栏快捷键：Ctrl+K
- ...

## 动作空间
click(start_box='(x,y)')
left_double(start_box='(x,y)')
right_single(start_box='(x,y)')
drag(start_box='(x1,y1)', end_box='(x2,y2)')
hotkey(key='ctrl k')
type(content='文本')
scroll(start_box='(x,y)', direction='down/up')
wait()
finished(content='完成说明')
failed(content='失败原因')

## 输出格式
Thought: [分析当前界面，说明下一步要做什么]
Action: [单个动作]
```

### 3.4 验证层

验证分两个粒度，不混用。

#### 粒度一：每步轻量验证（自动）

每次执行 Action 后，比较执行前后截图的像素哈希：
- 截图有变化 → 正常继续
- 截图无变化（连续 2 次）→ 触发自愈流程

不调用 VLM，成本极低。

#### 粒度二：检查点结构化断言（VLM 判断）

当 Agent 输出 `finished()` 或到达 DSL 中定义的 step checkpoint 时，触发一次独立 VLM 调用：

```
prompt:
  截图：[当前截图]
  断言："{checkpoint 文本}"
  
  这张截图是否满足上述断言？
  请严格回答：
  Result: PASS / FAIL
  Reason: [一句话说明，指出截图中的具体证据或缺失]
```

**关键设计**：断言是测试工程师在 DSL 里预先写好的具体视觉条件，不是让 VLM 自由发挥判断"是否成功"。这样幻觉风险低，结果可复现。

---

### 3.5 失败自愈模块

当以下任一情况发生时触发：
- 轻量验证连续检测到截图无变化
- 结构化断言返回 FAIL
- 单步超时

#### 自愈流程

```
1. 截取当前屏幕 + 记录失败的 intent 和 checkpoint
2. 构建自愈 prompt：
   "你正在执行：{intent}
    通过条件：{checkpoint}
    当前屏幕：[截图]
    上一步执行了：{last_action}
    但断言未通过，原因：{reason}
    
    请分析失败原因，给出替代操作方案。"
3. 模型输出替代 Action，重新执行
4. 最多重试 N 次（DSL 中 max_retries 配置）
5. 超过重试次数 → 标记该 step 为 FAIL，继续下一个 step（可配置是否中止）
```

## 四、关键技术选型

| 模块 | 选型 | 理由 |
|------|------|------|
| VLM 模型 | 豆包 2.0（Vision） | 官方提供 API，与 UI-TARS doubao 坐标格式对齐，action_parser 可直接复用 |
| Action 解析 | UI-TARS `action_parser.py` | 直接复用，支持 doubao 坐标格式，已有完整 pyautogui 代码生成 |
| 操作执行 | PyAutoGUI + pyperclip | 跨平台，type 动作走剪贴板粘贴解决中文输入问题 |
| 截图采集 | mss | 比 PIL 截图快，支持指定窗口区域 |
| DSL 格式 | YAML | 人可读，模型易生成，结构清晰 |
| 报告格式 | JSON + Markdown 摘要 | JSON 供程序消费，Markdown 供人阅读 |

## 五、创新点

### 5.1 DSL 生成层（核心差异化）

不是纯自然语言驱动（不可验证），也不是传统测试脚本（不可泛化）。中间层 DSL 把**测试意图**（intent）和**验证条件**（checkpoint）分开表达：

- intent 指导 Agent 做什么（灵活，允许模型自主寻路）
- checkpoint 定义成功标准（确定，是视觉可验证的具体条件）

测试工程师只需写自然语言，模型自动生成 DSL，人工可选审查后执行。

### 5.2 飞书 UI 知识注入

在 system prompt 中预置飞书桌面端的 UI 知识：导航结构、常见弹窗、快捷键约定等。对 generic VLM 而言，这些 app-specific 知识能显著减少"找不到按钮"类错误，减少平均步骤数。

### 5.3 失败自愈（Self-Healing Execution）

区别于 retry 重复同一动作，自愈是让模型**分析失败原因并设计替代路径**。这模拟了真实测试工程师遇到失败时的排查行为，也是课题加分项中明确提到的能力。

### 5.4 Electron 双通道验证（进阶）

飞书基于 Electron，可通过 `pywinauto`（Windows UIA）或 macOS Accessibility API 获取 UI 元素树。在检查点验证时，叠加 AT 查询作为补充信号（如确认按钮 enabled 状态、文本框内容），提升验证置信度。

**注意**：操作决策仍然基于视觉，AT 仅用于验证，不用于操作定位。

## 七、未来路线图（MVP 完成后）

> 当前文档聚焦 MVP。以下为后续演进方向，暂不实现，先做记录。

### V2：记忆系统与自进化

为 Agent 添加持久化记忆层，使系统能从历次执行中学习，不断优化自身行为。

**记忆内容**：
- 成功案例：哪种 intent → 哪种操作路径 → 成功，记录下来作为后续同类任务的参考
- 失败案例：哪种场景触发了自愈，根因是什么，最终用哪条替代路径通过
- 飞书 UI 变更记录：某个操作以前能找到的按钮现在找不到了，记录变更点

**应用方式**：
- 执行前 RAG 检索：根据当前 intent 召回相似历史案例，注入 prompt 作为参考轨迹
- 自动更新飞书 UI 知识库：从成功轨迹中提炼 UI 导航经验，丰富 system prompt
- 失败模式库：积累常见失败模式和对应自愈策略，减少重复探索

**自进化闭环**：
```
执行 → 结果（PASS/FAIL）→ 提炼经验 → 存入记忆 → 下次执行时召回 → 更少失败
```

这本质上是一个以测试执行为数据飞轮的持续学习系统，运行越多，越精准。

## 八、工程注意事项

**DPI 缩放**：Windows 高 DPI 屏幕需设置 DPI 感知，否则 pyautogui 坐标偏移：
```python
import ctypes
ctypes.windll.shcore.SetProcessDpiAwareness(1)
```

**渲染等待**：飞书某些操作（打开文档、网络请求）有异步加载，固定 sleep 不够用。应在轻量验证里检测截图变化，稳定后再进行下一轮。

**中文输入**：type 动作默认走剪贴板粘贴（UI-TARS action_parser 的 `input_swap=True`），飞书搜索框可能拦截 Ctrl+V，需测试并按情况回退到逐字符输入。

**坐标格式确认**：豆包 2.0 Vision 的坐标输出格式需实测，确认是否遵循 doubao 的相对坐标 × 1000 格式，据此设置 `model_type` 参数。
